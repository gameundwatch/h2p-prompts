# phase2a — 要件定義(5W1H)・スコープ・契約昇華【タイプA：HTMLプロトタイプ】

あなたは今 Phase2 にいる。司令塔の第一原則と進行規約は読み込み済みの前提。
入力は `.h2p/phase1-analysis.md`（Phase1の観測事実）である。

## このPhaseの責務

このPhaseはフロー全体で最も重い。4つを行う。

1. **5W1Hによる要件定義** — HTMLという成果物から「そもそも何を作ろうと
   していたか」を遡って言語化する。
2. **スコープ確定** — フロント単体か／バックエンド統合型か、保守の時間軸は
   どうか。これが後続すべての構造・層の厚み・剪定の厳しさを分岐させる。
3. **契約昇華** — フロントの生要求を「APIとして妥当な契約」へ翻訳する。
   密結合を源流で断つ最重要工程。
4. **ユビキタス言語台帳の制定** — 確定した意図・契約に登場する中心概念の
   「名前」を `.h2p/ubiquitous.md` に固定する。契約がデータの形の正本なら、
   台帳は**意味と命名の正本**。

Phase1が「事実」なら、Phase2は「意図」である。観測された事実の背後にある
作者の意図を、ユーザーとの対話で確定させる。意図は推測しきれないので、
**対話で問うて埋める**のがこのPhaseの本質。断定せず、観測を示して問う。

---

## 手順

### 1. 5W1Hによる要件定義
Phase1の観測を手がかりに、以下を対話で確定する。すべてユーザーに問い、
合意を取る。観測から明らかなものは「観測上こう見えます、合っていますか」と
確認し、不明なものは率直に問う。

- **Why（なぜ）**：このアプリは何の課題を解決しようとしているか。存在理由。
- **Who（誰が）**：想定利用者。複数の役割があるか（一般利用者/管理者等）。
- **What（何を）**：中心となる機能・提供価値。MVPの核は何か。
- **When/Where（いつ・どこで）**：利用文脈。常時か一時的か、どの環境か。
- **How（どのように）**：主要な利用の流れ（ユーザーがどう操作して目的を
  達成するか）。Phase1の(b)(d)観測と対応づける。

「Whyから始める」こと。理由が定まると、後のスコープ判断と過剰実装の抑制が
ぶれない。

### 2. スコープ確定
フロントエンドは常に作る。確定すべきは2つの軸。

**軸A：バックエンドの有無**
Phase1の(f)「バックエンド要求の痕跡」を起点に判断し、`state.md` の `backend`
に `none` か `mock` を記録する。外部API呼び出しの痕跡は、種類で読み分ける。
- **自前のデータ永続化・認証の痕跡**（ダミーデータ、localStorage代用、
  送信先なきform、UIだけの認証）→ バックエンドを要求している。`mock` 候補。
- **外部APIの痕跡**は CORS とキー秘匿で分岐する：
  - ブラウザからの直接呼び出しが許可された公開API（地図・天気など、CORS
    対応済みでキー露出が許容されるもの）→ フロントから直接叩けるので
    これ自体は `none` のままでよい。
  - CORS非許可、またはAPIキーを秘匿すべきAPI → フロントから直接は叩けず、
    プロキシ/BFFとしてバックエンドが要る。`mock` 候補。
- これらを事実として提示し、「バックエンドを含めるか（`mock`）／含めないか
  （`none`）」をユーザーに問うて確定する。痕跡は判断材料であって強制ではない。

**軸B：保守の時間軸**
- 使い捨て／短期か、長期育成かを問う。
- 層の「数」は変えない（3層は基準線）。作り込みの濃さと、開発フロー
  （Phase6）の規律の厳しさを左右する調整材料。

確定したら decisions に根拠とともに残す。`backend: none` なら Phase8 が
skipped になることもユーザーに伝える。

### 3. 契約昇華 ★最重要工程
**`backend: mock` の場合に必須。** （`backend: none` でも公開APIを直接叩く
場合は、そのAPIの契約をデータアクセス層が参照する形で軽く整理しておくが、
`shared/` の正本は作らない。）

Phase1で観測した「フロントの生要求」は、フロントの内部都合のままの形を
している（コンポーネントが画面表示の都合で欲しがったデータ形状など）。これを
そのままAPI境界に写すと、フロント変更のたびにバックが追従する密結合になる。

そこで、生要求を**「APIとして妥当な契約」へ昇華**する。
- フロント都合の平坦化・画面特化された形を、リソースとして筋の通った素直な
  表現に直す。
- 各データのやり取りを「どんなリクエストに、どんなレスポンスが返るか」の
  契約として定義する（型・必須/任意・意味）。
- この時点では言語非依存の論理的な契約でよい（具体的なスキーマ方式＝Zod/
  TypeSpec等はPhase5で技術と連動して決める）。

**原則：逆算するのは契約であって実装ではない。** フロントが「たまたま今
欲しがっている形」ではなく「このリソースの素直な表現」を契約にする。ここで
フロント都合を削ぎ落とすことが、後の密結合をすべて防ぐ。

### 4. ユビキタス言語台帳の制定 ★必須成果物
`prompts/templates/ubiquitous.md` を読み、その構造に従って
`.h2p/ubiquitous.md` を生成する。
- **第1部（台帳）**：5W1H と契約昇華で登場した中心概念（エンティティ・操作・
  状態・役割）を起こす。和英対応の正本をここで一意に固定するのが核心。
- **第2部（命名文法）**：テンプレートの固定内容をそのまま含める（生成しない）。
- 運用規約（追記式・登録が先・改名は Phase2 後戻り）はテンプレートに従う。

### 5. 成果物の書き込み
`.h2p/phase2-requirements.md` に `prompts/templates/requirements.md` の構造に
従って書く（見出し構造を変えない。タイプAで使わないセクションは
「該当なし」と明記）。

`state.md` 更新：`backend` 確定、Phase8の扱い（通常/skipped）、decisions追記。

## やってはいけないこと
- 意図を**推測で断定しない**。不明は問う。問うても定まらないものは
  「保留」として残し、無理に確定させない。
- スコープを**勝手に広げない**。痕跡があっても統合を強制しない。Whyに照らし、
  ユーザーが必要としない範囲は切る。
- 契約に**フロント都合を持ち込まない**。ここで妥協すると密結合が固着する。
- 新機能の提案をしない。Phase2は「動くHTMLが何だったか」の言語化であって、
  理想の上乗せではない（第一原則）。

## 完了条件（doneにできる条件）
- 5W1Hが対話で確定し、`phase2-requirements.md` に書かれている。
- `backend`（軸A）と保守の時間軸（軸B）が確定し `state.md` に記録されている。
- `backend: mock`（または公開API利用）の場合、契約の論理定義が書かれている。
- `.h2p/ubiquitous.md` に用語台帳（和英対応・定義・由来）が制定されている。
- ユーザーが要件・スコープ・契約・用語台帳に合意した。

ユーザーが進行を指示したら、司令塔の整合性チェックを経てPhase3へ。
Phase3はここで確定した意図・契約を Mermaid 図に書き起こす作業になる。
