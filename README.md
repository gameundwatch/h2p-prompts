# html-to-project

動いている **HTMLプロトタイプ**（1枚でも、数枚で1つのアプリでも）を、
設計意図を保ったまま、そのまま開発を始められる **フロントエンド
（必要ならフルスタック）プロジェクト** へ移行するためのプロンプト集です。

すでに `package.json` を持つ **既存のフロントエンドプロジェクト** を、
機能を変えずに「機能を増やせる構造」へ整理し直す用途にも対応しています。

Claude Code のようなエージェント環境に読み込ませて使います。ツール本体は
プロンプト（Markdownファイル）の集まりで、特別なインストールは要りません。

---

## これは何をするものか

1枚のHTMLファイルは、手軽に動くプロトタイプを作れる一方、いざ本格開発に
移そうとすると、コンポーネント分割・状態管理・ビルド環境・フロント/バックの
分離などが未整理のままで、手を入れにくくなります。

このツールは、その移行を **9つの段階（Phase）** に分けて、エージェントと
あなたの対話で進めます。いきなりコードを書き換えるのではなく、

- まず入力を **観測**し（このとき「挙動チェックリスト」を作ります）、
- 「そもそも何を作ろうとしていたか」を **言語化**し（用語集もここで作ります）、
- 構造を **図**にして合意し、
- 動くHTMLのまま **設計意図に沿って整え**、
- スコープに合った **技術を選び**（不要なものは入れない）、
- **開発環境を立ち上げて実装**し、
- **ドキュメント**にまとめて閉じる

という流れをたどります。各段階の節目で「まだ同じように動くか」を
チェックリストで必ず確認するので、**理想を盛り込んで動かなくなる**ことを
防げます。

### 大事な前提
- 対象は **すでに動いているもの**です。動かないものを直す道具ではありません。
- 進むタイミングを決めるのは **あなた**です。エージェントは勝手に次へ進みません。
- 機能の追加や「改善」は基本しません。**今あるものを忠実に移行**します。
- 見た目や操作感が同じかどうかの**最終確認はあなたの役目**です。エージェントは
  比較用のページを用意してあなたの確認を手伝います。

### 2種類の入力
- **タイプA：HTMLプロトタイプ** … `.html` が中心（1枚でも複数枚でも、
  CDNでReactやTailwindを読み込んでいてもOK）。構造をゼロから与えます。
- **タイプB：既存フロントエンドプロジェクト** … `package.json` とソース一式が
  あるもの。現状を診断し、機能を保ったまま構造を段階的に作り変えます。

どちらかはエージェントが起動時に自動判別します（曖昧なら確認されます）。

## 必要なもの

- Claude Code など、ファイルの読み書きとコマンド実行（bash）ができる
  エージェント環境。
- 移行したい **動く入力**（HTML一式、または既存プロジェクト）。
- Node.js など、選んだ技術スタックに必要な実行環境（実装段階で使います）。
- git（履歴管理に使います。リポジトリでなければエージェントが `git init`
  します）。

## 配置のしかた

作業用のフォルダを用意し、**このプロンプト集** と、**あなたの入力を入れた
`origin/` フォルダ** を置きます。

```
my-project/                  ← 作業フォルダ（最終的にここがプロジェクトになる）
├── prompts/                 ← このツール本体
│   ├── orchestrator.md      ←   司令塔。最初にこれを読ませる
│   ├── a_html/              ←   タイプA用の指示書（phase1a〜3a）
│   ├── b_frontend/          ←   タイプB用の指示書（phase1b〜3b）
│   ├── phase4.md 〜 phase9.md ← 後半の共通指示書
│   └── templates/           ←   成果物の雛形置き場
│       ├── state.md         ←     進行状態ファイル
│       ├── ubiquitous.md    ←     用語台帳＋命名文法（辞書的命名の固定辞書）
│       └── analysis.md / requirements.md / structure.md / stack.md
│
├── origin/                  ← あなたの入力はここに置く
│   └── index.html           ←   HTML一式、または既存プロジェクト一式
│
└── README.md                ← この説明書
```

> **入力をルート直下に置いてしまっても大丈夫です。** 起動時にエージェントが
> 検出し、あなたに確認した上で `origin/` へ移動します。
>
> **`origin/` の中身は移行中ずっとそのまま残ります。** 作業はすべてコピーに
> 対して行われ、`origin/` は「元はこう動いていた」という基準点として
> 最後まで保全されます。

## 起動のしかた

エージェントに、まず **司令塔プロンプト `orchestrator.md` を読ませる**だけです。
作業フォルダで以下のように伝えてください（言い回しは自由です）。

```
prompts/orchestrator.md を読んで、その指示に従ってください。
origin/ に入れたHTMLをプロジェクトに移行したいです。
```

エージェントは起動すると、

1. git リポジトリでなければ `git init` し（以降、節目ごとに記録が残ります）、
2. 作業状態を記録する `.h2p/state.md` を作り（初回のみ）、
3. 入力タイプを判別して（タイプAならHTMLを `.h2p/source/` へコピー、
   タイプBなら作業用コピーをルートに展開して）、
4. 最初の段階（Phase1：分析）から対話を始めます。

あとは画面の案内に沿って対話を進めるだけです。

### 次の段階へ進むには
各段階の作業が終わると、エージェントが結果を提示します。内容を確認し、
よければ **あなたから明示的に「次へ進んで」と伝えてください**。エージェントは
あなたの指示があるまで次の段階へは進みません。各段階の成果は逐一ファイルに
記録されるので、途中で中断しても大丈夫です。

### 中断・再開について
セッションが切れたり日をまたいでも、再び `orchestrator.md` を読ませれば、
`.h2p/state.md` から **今どこまで進んだか**を読み取って続きから再開します。
長い作業になるので、無理に一度で終わらせる必要はありません。

### やり直したいとき
ある段階の結果に納得できず前の段階に戻りたい場合は、「Phase◯ に戻りたい」と
伝えてください。戻った段階より後の成果はやり直しになります（その旨エージェントが
説明します）。コードの状態は節目ごとに git にコミットされているので、
壊れても戻れます。

## 進行する9つの段階

| 段階 | 何をするか | あなたの関わり方 |
|------|-----------|----------------|
| 1 | 入力を観測し、挙動チェックリストを作る | 観測結果を確認。複数HTMLなら対象を選ぶ |
| 2 | 「何を作ろうとしていたか」を言葉にし、範囲と用語集を決める | 5W1Hの問いに答え、バックエンドの有無を決める |
| 3 | 構造・データ・状態・流れを図にする | 図が意図に合っているか確認（図はHTMLでも見られます） |
| 4 | 動くHTMLのまま、意図に沿って整える | 比較ページで「同じ動きか」を確認 |
| 5 | 技術を選ぶ（不要なものは入れない） | 候補が複数あるものを **あなたが選ぶ** |
| 6 | 開発の進め方・規律を決める | 規模に合った進め方に合意 |
| 7 | 開発環境を立ち上げ、フロントを実装 | 比較ページで元と同じ動きか確認 |
| 8 | （必要時）バックエンドのモックを作り結合 | フロントと繋がって動くか確認 |
| 9 | ドキュメント化して仕上げる | 完成と片付けに合意 |

> 段階5の技術選びでは、エージェントが「この機能が要るか」までは判断しますが、
> 「どのライブラリにするか」候補が複数あるものは **あなたの好みや慣れ**に
> 合わせて選んでもらいます。あなたが保守していくものだからです。

> 段階8は、バックエンドが必要だと段階2で決めた場合だけ実行されます。フロント
> だけで完結するなら飛ばします。

> 「同じ動きか」の確認では、エージェントが `.h2p/review/` に**比較用のHTML
> ページ**（元と新を並べて表示し、チェックリストを添えたもの）を用意します。
> あなたはそれを開いて、1項目ずつ確認するだけです。違いがあってもあなたが
> 「これでよい」と認めたものは、記録に残した上で先へ進めます。

## 完成すると

作業フォルダの直下に、そのまま開発を始められるプロジェクトが残ります。

```
my-project/
├── CLAUDE.md          ← プロジェクトの指針（今後の開発でエージェントが従う）
├── README.md          ← プロジェクトの説明・起動手順（この説明書と置き換わる）
├── documents/         ← 設計の記録（要件・図・用語集・技術選定の理由）
├── frontend/          ← フロントエンド一式
├── backend/  shared/  ← バックエンドが必要だった場合のみ
├── origin/            ← あなたの元の入力（そのまま）
└── .h2p-archive/      ← このツールの作業記録（片付け後）
```

開発環境（開発サーバー）が起動する状態まで仕上がっているので、すぐに開発を
続けられます。

### 片付けについて
移行が終わると、ツール本体（`prompts/`）と作業フォルダ（`.h2p/`）は
`.h2p-archive/` へまとめて片付けられ、この説明書もプロジェクト自身の
README に置き換わります。作業記録は git の履歴にも残るので、`.h2p-archive/`
を消すかどうかは最後にあなたが選べます（勝手には消しません）。

## つまずいたら

- **エージェントが勝手に進む / 進まない** … 進行はあなたの明示指示が合図です。
  「次へ進んで」「まだ確認したい」とはっきり伝えてください。
- **今どこにいるか分からなくなった** … `.h2p/state.md` を開けば現在地と
  これまでの決定が読めます。エージェントに「今の状態を教えて」と聞いても
  構いません。
- **動かなくなった気がする** … 各実装段階の出口で、チェックリストを使った
  動作確認をする設計です。確認が通らないうちは次へ進めないので、その段階で
  一緒に直してください。節目ごとのコミットがあるので、直前の動く状態にも
  戻れます。
- **元の入力を失わないか不安** … `origin/` の中身は移行中いっさい変更されず、
  最後までそのまま残ります。作業はすべてコピーに対して行われます。
